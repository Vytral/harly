---
title: "API authorization"
description: "Choose API key scopes and understand how Harly applies workspace permissions, role limits, and write attribution."
---

An API key belongs to one workspace. Give it only the scopes the integration
uses, and store secret keys on the server. A publishable key can read public
jobs and submit applications to them.

## How a request is authorized

1. Harly checks the key. Unknown, revoked, and expired keys return `401`.
   From Harly 0.5.1, keys whose creator leaves the workspace, is deactivated,
   or has their account deleted also stop working.
2. Harly checks the key type and required scope. Send a secret key in the
   `Authorization` or `x-api-key` header. Publishable keys can also use the
   `pk` query parameter and only hold `jobs:read` and `applications:write`.
3. Harly applies [rate limits](/developers/api-overview#rate-limits) and any
   additional checks the endpoint requires. For example, the workspace
   activity feed requires an unrestricted role for the key creator.

API key scopes and the role limits you set in the dashboard are separate.
Use the scope table to restrict what the key can do. Treat a secret key as
workspace-wide unless the endpoint documents a narrower limit.

## Create and rotate keys

In the dashboard, key management requires `integrations:manage`. To create or
rotate a key through the API, use a secret key with `api_keys:write` and the
scopes you want to assign. It can grant only scopes it already holds. Use the
[API key reference](/developers/api-reference) for rotation and revocation.

## Who appears on a write

When an endpoint needs a workspace member to record who performed a write, it
uses the member who created the key. The activity entry identifies that member.
Reissue integration keys from an active account before removing their creator.

## Scope inventory

These scopes apply to the authenticated `/api/v1` routes. The legacy
`webhooks:manage` scope covers both webhook scopes.

| Scope | Endpoints |
| --- | --- |
| `jobs:read` | `GET /jobs`, `GET /jobs/{id}` |
| `jobs:write` | `POST /jobs`, `PATCH /jobs/{id}`; also covers `jobs:publish` and `jobs:delete` for keys created before they existed |
| `jobs:publish` | `POST /jobs/{id}/publish`, `POST /jobs/{id}/close` |
| `jobs:delete` | `DELETE /jobs/{id}` |
| `stages:read` | `GET /jobs/{id}/stages` |
| `stages:write` | Create, update, reorder, archive, and delete job stages |
| `candidates:read` | `GET /candidates`, `GET /candidates/{id}` |
| `candidates:write` | `POST /candidates`, `PATCH /candidates/{id}`, `DELETE /candidates/{id}` |
| `notes:read` / `notes:write` | List and create candidate notes |
| `tags:read` / `tags:write` | List, add, and remove candidate tags |
| `files:read` | `GET /candidates/{id}/files` |
| `applications:read` | `GET /applications`, `GET /applications/{id}` |
| `applications:write` | Create, move, and bulk-create applications; also covers `applications:reject` and `applications:hire` for older keys |
| `applications:reject` | `POST /applications/{id}/reject` |
| `applications:hire` | `POST /applications/{id}/hire` |
| `interviews:read` / `interviews:write` | List, read, schedule, update, cancel, and complete interviews |
| `offers:read` / `offers:write` | List, read, draft, update and send offers; `offers:write` also covers `offers:decide` for older keys |
| `offers:decide` | Record a decision on an offer and withdraw it |
| `scorecards:read` / `scorecards:write` | List and create scorecards |
| `tasks:read` / `tasks:write` | List, read, create, update, and delete tasks |
| `pool:read` / `pool:write` | List, add, remove, and assign talent-pool entries |
| `activity:read` | `GET /activity-events`. Returns `403` if the key creator's role is limited to specific jobs. |
| `webhooks:read` / `webhooks:write` | List and read endpoints and deliveries; create, update, delete, test, and replay |
| `api_keys:read` / `api_keys:write` | List keys; create, delete, and rotate keys |
| none | `GET /me` |

## Creating keys with finer scopes

Keys created before `jobs:publish`, `jobs:delete`, `applications:reject`,
`applications:hire` and `offers:decide` existed keep working: the umbrella scope
still satisfies the finer ones. To create a new key with `jobs:write`,
`applications:write` or `offers:write`, the creator's role must also hold the
permissions those scopes still reach (publish, delete, reject, edit, decide).
Prefer the finer scopes for new integrations.
