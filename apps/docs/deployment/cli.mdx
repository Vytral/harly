The Harly CLI installs and operates a self-hosted Harly deployment. It
generates the Docker Compose topology, creates independent runtime secrets,
waits for service readiness, and provides safe day-two operations such as
backups and upgrades.

## What you will learn

- Check a host before installing Harly.
- Generate and launch a local Docker deployment.
- Automate the installer from CI or an agent without unexpected prompts.
- Provision Railway or prepare Fly.io and DigitalOcean deployments.
- Check an installation at a glance with `harly status`.
- Interpret JSON results, exit codes, and readiness failures.

## Prerequisites

For a local VPS installation, install:

- Node.js 20.12 or newer.
- Docker Engine 24 or newer.
- Docker Compose 2.20 or newer.
- At least 5 GB of free disk space by default.
- A public DNS record when using Caddy or an external HTTPS proxy.

Run the host check first:

```bash
npx --yes @harly/cli check
```

The check reports Docker, Compose, memory, disk, firewall, and the public
ports used by the selected deployment topology.

## Install Harly locally

### Run the guided installer

```bash
npx --yes @harly/cli
```

On a fresh host, the menu opens the installer. It asks for the public URL,
proxy mode, owner email, organization name, storage provider, and resource
profile. Before writing files it shows a complete summary.

The installer then:

1. Validates Docker, Compose, ports, disk, memory, firewall, and DNS.
2. Resolves a pinned Harly release image.
3. Creates `.env`, `compose.yaml`, `Caddyfile`, `harly.config.json`, and local operator documentation.
4. Generates independent runtime secrets and protects `.env` with mode `0600`.
5. Optionally pulls images and launches the services.
6. Waits for PostgreSQL, migrations, the web app, the scheduler, and Caddy.
7. Checks `/api/health/ready`. Automatic HTTPS requires a successful public response before reporting `Harly is ready`.

### Generate configuration without launching

```bash
npx @harly/cli init ./harly \
  --url https://careers.example.com \
  --proxy caddy \
  --email owner@example.com \
  --organization "Acme Inc."
```

`init` writes configuration but does not pull images or start containers. Run:

```bash
npx @harly/cli launch ./harly --yes
```

To do both steps in one command, add `--launch` to `init`.

### Resume an interrupted installation

After configuration has been saved, use **Start or resume installation** in the
guided menu or run:

```bash
npx @harly/cli resume ./harly --yes
```

This reuses the saved answers and secrets, validates configuration, pulls any
missing images, and reconciles existing containers. Resolve the reported error
before retrying. Without a directory, `resume` checks the current installation
and then the exact `./harly` default. You can preview the target with `--dry-run`.

Caddy is checked after the application is ready. It waits up to 15 minutes for
the public readiness endpoint to succeed, allowing time for DNS and automatic
HTTPS. Other services wait up to 90 seconds each. To change the per-service
timeout for `launch` or `resume`, add `--timeout <seconds>`.
The CLI reports elapsed time and the latest connection or HTTP status while
waiting. On timeout, it shows how to inspect Caddy's logs and retry.

### Install the CLI globally

When you run the CLI through npx in a terminal, it asks once:
`Install Harly globally so you can just type harly?` The default answer is yes.
The CLI asks at the start of the interactive menu and after `init`, `launch`,
and `resume`. After installing, it checks that `harly` resolves. If npm's global
bin directory is not on your `PATH`, it prints the exact command to add it for
zsh, bash, fish, or PowerShell.

The offer follows these rules:

- It is skipped when the CLI is already installed globally.
- `--yes` never accepts it implicitly.
- It is never shown in CI, in pipes, or with `--json`.
- Declining, cancelling, or an npm permissions error keeps the deployment successful. You can keep using `npx @harly/cli`.

The CLI remembers a declined offer in `config.json` under
`$XDG_CONFIG_HOME/harly` (default `~/.config/harly`), or `%APPDATA%\harly` on
Windows. Set `HARLY_CONFIG_DIR` to use another directory.

To install the CLI explicitly at any time, run `install-global`:

```bash
npx @harly/cli install-global          # asks first in a terminal
npx @harly/cli install-global --yes    # for scripts
npx @harly/cli install-global --dry-run
```

`--dry-run` previews the installation without running it.

`harly update` upgrades the application. Upgrade the global CLI separately with
`npm install -g @harly/cli@latest`.

### CLI update notices

In a terminal, the header notes when a newer CLI version is published. The CLI
checks the npm registry at most once a day, with a short timeout. Set
`HARLY_NO_UPDATE_CHECK=1` to turn the check off. It never runs in CI, with
`--json`, or with `--quiet`.

## Configure installer inputs

Public values can be passed as flags:

| Flag | Values |
| --- | --- |
| `--url <origin>` | Complete HTTP(S) origin, such as `https://careers.example.com`. A protocol is required. |
| `--domain <hostname>` | Convenience form normalized to an HTTPS origin. |
| `--proxy <mode>` | `caddy`, `external`, or `local`. |
| `--port <number>` | Host port for `external` and `local`. |
| `--email <address>` | Initial owner email. |
| `--organization <name>` | Organization display name. |
| `--storage <provider>` | `local` or `s3`. |
| `--resource-profile <profile>` | `compact`, `standard`, or `performance`. |
| `--image <reference>` | Exact version, `:latest`, or a digest. `:latest` is pinned to the current stable digest. `edge` is rejected. |
| `--output-dir <directory>` | Alias for the `init` positional directory. |
| `--launch` | Launch after generation. |
| `--no-launch` | Generate only. |

`init ./harly` and `init --output-dir ./harly` refer to the same target. If
both are provided with different paths, the command fails instead of choosing
one silently.

S3 values should come from the environment:

```bash
HARLY_INITIAL_ADMIN_EMAIL=owner@example.com \
STORAGE_PROVIDER=s3 \
S3_BUCKET=harly-production \
S3_REGION=auto \
S3_ACCESS_KEY_ID=... \
S3_SECRET_ACCESS_KEY=... \
npx @harly/cli init ./harly \
  --url https://careers.example.com \
  --non-interactive
```

The supported environment values are:

| Variable | Purpose |
| --- | --- |
| `HARLY_URL` | Public origin when `--url` is not supplied. |
| `HARLY_PROXY_MODE` | Proxy mode when `--proxy` is not supplied. |
| `HARLY_PORT` | Host port. |
| `HARLY_INITIAL_ADMIN_EMAIL` | Initial owner email. |
| `HARLY_ORGANIZATION` | Organization name. |
| `HARLY_RESOURCE_PROFILE` | Resource profile. |
| `HARLY_IMAGE_REF` | Pinned image override. |
| `STORAGE_PROVIDER` | `local` or `s3`. |
| `S3_BUCKET` | S3 bucket name. |
| `S3_REGION` | S3 region, default `auto`. |
| `S3_ACCESS_KEY_ID` | S3 access key. |
| `S3_SECRET_ACCESS_KEY` | S3 secret key. |
| `S3_ENDPOINT` | Optional S3-compatible endpoint. |
| `S3_PUBLIC_URL` | Optional public object URL. |

## Get help

Run `harly --help` to list commands grouped by purpose, with global options and
examples. For one command's options and examples, run either form:

```bash
harly help status
harly status --help
```

`harly --json help` returns the command list under `commands` and the grouping
under `groups`.

If you mistype a command or option, the CLI suggests the closest match instead
of printing the full help:

```text
$ harly docter
Did you mean harly doctor?
```

Failures end with suggested next steps. With `--json`, these are returned under
`next`. Add `--verbose` to include the stack trace for unexpected errors.

## Automate the CLI

Global flags work before or after a subcommand when unambiguous:

```text
--json --quiet --no-color --verbose --non-interactive --yes --dry-run --force --timeout <seconds>
```

`--quiet` hides the header, hints, and update notices but keeps results and
errors. `--no-color`, or the `NO_COLOR` environment variable, removes color from
all output.

Use `--non-interactive` in CI and agent workflows. It never prompts; missing
values fail before host or provider operations begin.

### JSON output

`--json` disables prompts and loaders. stdout contains exactly one JSON document
for success, failure, and cancellation. Human diagnostics, when enabled, are
written to stderr only.

Example dry run:

```bash
npx @harly/cli --json init ./harly \
  --dry-run \
  --url http://127.0.0.1:3000 \
  --proxy local \
  --email owner@example.com
```

The result is versioned:

```json
{
  "schemaVersion": 1,
  "ok": true,
  "status": "dry-run",
  "command": "init",
  "sideEffects": false,
  "artifacts": [".env", "compose.yaml", "harly.config.json"]
}
```

Failures use the same schema:

```json
{
  "schemaVersion": 1,
  "ok": false,
  "status": "failed",
  "command": "init",
  "error": {
    "code": "MISSING_ARGUMENT",
    "message": "--email or HARLY_INITIAL_ADMIN_EMAIL is required."
  }
}
```

Stable error codes include `INVALID_ARGUMENT`, `MISSING_SECRET`,
`PREFLIGHT_FAILED`, `READINESS_TIMEOUT`, and `PARTIAL_PROVISIONING`.

### Secrets and stdin

Never pass secrets as ordinary flags. Use environment variables or one
explicit stdin source per execution:

```bash
printf '%s\n' "$RAILWAY_TOKEN" |
  npx @harly/cli --json deploy railway --railway-token-stdin \
    --project-name harly-production \
    --email owner@example.com
```

The CLI never accepts a JSON blob of secrets, never reads stdin implicitly,
and never prints secrets in JSON, logs, or error messages.

### Dry runs

`--dry-run --json` resolves the configuration and lists artifacts and planned
remote operations. It does not:

- Write files or create directories.
- Download images.
- Run Docker Compose.
- Call provider APIs.
- Create cloud resources.
- Save secrets.

## Deploy to managed platforms

### Railway

Railway is the fully automated cloud provider. Set secrets through the
environment and run:

```bash
RAILWAY_TOKEN=... \
S3_BUCKET=harly-production \
S3_ACCESS_KEY_ID=... \
S3_SECRET_ACCESS_KEY=... \
npx --yes @harly/cli deploy railway \
  --project-name harly-production \
  --email owner@example.com \
  --non-interactive
```

The CLI creates the project, managed PostgreSQL, volume, web service,
scheduler, migration service, runtime variables, domain, and deployments. It
waits for the public readiness endpoint before returning `status: "ready"`.

Railway secrets are not saved locally by default. Add `--save-env` only when a
local copy is explicitly required:

```bash
npx @harly/cli deploy railway --save-env
```

The resulting file has mode `0600`, and the CLI prints a warning. If Railway
fails after creating resources, JSON includes `status: "failed"`,
`error.code: "PARTIAL_PROVISIONING"`, `resourcesCreated`, and recovery steps.
Resources are not deleted automatically.

When `--url` or `--domain` is supplied, the generated Railway domain remains
the verified deployment URL. The requested custom domain is returned as
`requestedUrl` with an explicit follow-up step to attach and verify it in
Railway.

### Railway Config as Code

The repository also includes [`railway.toml`](https://github.com/vytral/harly/blob/main/railway.toml). Railway detects
this file automatically and applies its Dockerfile, web start command,
readiness path, and restart policy to the current service deployment. This is a
service-level configuration file, not a full project manifest: it does not
create PostgreSQL, the scheduler, or the migration service. Use the CLI API
flow above when you need the complete Harly topology.

### Fly.io and DigitalOcean

These providers currently use a preparation flow and finish with
`status: "ready-to-deploy"`:

```bash
npx @harly/cli deploy fly prepare \
  --url https://careers.example.com \
  --email owner@example.com

npx @harly/cli deploy digitalocean prepare \
  --url https://careers.example.com \
  --email owner@example.com
```

The CLI writes `fly.toml` or `app.yaml`, validates the resolved configuration,
and prints the exact provider commands still required. It does not create
provider resources. The repository's [`.do/app.yaml`](https://github.com/vytral/harly/blob/main/.do/app.yaml) is the
canonical DigitalOcean App Platform spec and can also be used directly with
`doctl apps create --spec .do/app.yaml` or
`doctl apps update APP_ID --spec .do/app.yaml`; it provisions the multi-service
App Platform topology. Use `--save-env` if you explicitly need a local `0600`
secrets file.

## Operate an installation

### See installation status

`status` summarizes an installation on one screen and suggests next steps:

```bash
harly status ./harly
```

```text
INSTANCE
✓ URL      https://ats.example.com  answers ready · 120 ms
✓ Version  v0.2.4  latest
SERVICES
✓ Database     running · healthy
✓ Application  running · healthy
HOST
✓ Disk         23.4 GB free
✓ Last backup  2 days ago · 12 MB
✓ Certificate  Let's Encrypt · expires in 61 days
```

The CLI only shows what it can verify:

| Item | Source |
| --- | --- |
| URL | The public `/api/health/ready` endpoint. |
| Version | The running version compared with the release manifest. Offline, it shows `latest unknown`. |
| Containers and database | `docker compose ps`. |
| Disk | Free space on the host. |
| Last backup | The newest archive in `backups/`. |
| Certificate | A TLS handshake with the public host. |

Warnings do not change the exit code. These include a backup older than a week,
low disk space, a certificate expiring within 14 days, or a newer release.
`status` exits `1` when a service is stopped or the readiness check fails, so
you can use it in monitoring scripts. `--json` prints the same data as one JSON
document.

`doctor` is unchanged. Use it for detailed checks and `--fix`.

### Check readiness

```bash
npx @harly/cli doctor ./harly
npx @harly/cli --json doctor ./harly
```

Use `doctor --fix` only in an interactive terminal. It can restart stopped
services or bring the Compose project back up.

### Back up before updates

```bash
npx @harly/cli backup ./harly
npx @harly/cli update
```

Run `update` from the installation directory, or from any directory inside it.
It reads the current stable release and moves this install there. It does
nothing when that version is already running. `--to 0.2.1-beta.1` opts into a
prerelease. The flow creates a rollback archive, pulls that exact version,
runs the database migration once, restarts the services, and waits for
readiness.

Before running any migration, `update` checks the pulled release's image
digest against the release manifest. If the digests differ, `update` refuses
the release.

`update` does not rewrite `compose.yaml`. Installations generated by an older
CLI keep their original file. See
[Database pool settings in compose.yaml](#database-pool-settings-in-compose-yaml).

### Update from the app

`harly updater` is the host-side half of **Settings → Updates** in the app:

```bash
harly updater install-service ./harly   # install and start a systemd service
harly updater status ./harly
harly updater run                       # run under another supervisor
```

The updater polls the instance for requested and scheduled updates, runs
`harly update`, and rolls back if the update fails. See
[Update from the app](/self-hosting/operations#update-from-the-app) for setup
and options.

### Database pool settings in compose.yaml

`harly init` writes a `compose.yaml` that forwards these database pool sizes
from `.env` to the app and scheduler:

| Variable | Purpose |
| --- | --- |
| `HARLY_DB_POOL_MAX` | Main connection pool size. Default `10`. |
| `HARLY_DB_LOCK_POOL_MAX` | Dedicated pool for cron advisory locks. Default `20`. |
| `HARLY_DB_MAILBOX_LOCK_POOL_MAX` | Dedicated pool for mailbox-sync advisory locks. Default `4`. |

An existing installation keeps its old `compose.yaml`, and `harly update` does
not rewrite it. To set these values on an existing install, add the lines by
hand under `x-env: &env` in `compose.yaml`:

```yaml
x-env: &env
  # ...existing entries
  HARLY_DB_POOL_MAX: ${HARLY_DB_POOL_MAX:-}
  HARLY_DB_LOCK_POOL_MAX: ${HARLY_DB_LOCK_POOL_MAX:-}
  HARLY_DB_MAILBOX_LOCK_POOL_MAX: ${HARLY_DB_MAILBOX_LOCK_POOL_MAX:-}
```

Then set the values in `.env` and restart the services with
`docker compose up -d`.

### Restore or uninstall

```bash
npx @harly/cli restore ./harly/backups/harly-2026-01-01.tar.gz ./harly --force
npx @harly/cli uninstall ./harly
```

Restore replaces the current database and uploads. Back up first. The
`--remove-data` option for uninstall permanently removes PostgreSQL and upload
volumes; it is intentionally separate from the default uninstall behavior.

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Successful completion. |
| `1` | Operational failure. `status` also exits `1` when a service or the public endpoint is down. |
| `2` | Invalid usage or configuration. |
| `130` | Ctrl+C cancellation. |

## Troubleshooting

### Caddy cannot bind ports 80 or 443

Check the process reported by the installer. Stop or reconfigure the existing
proxy, or use `--proxy external` and forward traffic to the Harly host port.

### DNS validation fails

Create an A record for the public hostname and allow propagation. Verify it
from the VPS with:

```bash
dig +short A careers.example.com
```

### The public readiness check times out

Run:

```bash
npx @harly/cli doctor ./harly
docker compose -f ./harly/compose.yaml ps
docker compose -f ./harly/compose.yaml logs --tail=100 app scheduler migrate
```

Check the domain, firewall, database migration, and proxy mode before retrying.
