`HARLY_URL` is the canonical public origin. Use a bare origin without a path:
`https://hiring.example.com`. Every secret must be independent — do not reuse
values between variables. The older `NEXT_PUBLIC_APP_URL` and
`BETTER_AUTH_URL` variables still work as temporary fallbacks for `HARLY_URL`
and log a deprecation warning. Production startup fails before accepting
traffic when a required value is missing or malformed.

## `HARLY_URL` validation

Harly derives every public URL from `HARLY_URL` rather than the incoming
request origin. That includes upload presign URLs, authenticated file URLs,
OAuth callbacks, redirects, page metadata, outbound webhook payloads,
candidate notifications, and integration callbacks. A misconfigured value
therefore leaks into links your candidates and integrations receive, so Harly
validates it at startup and refuses to boot when it is unsafe.

In production (`NODE_ENV=production`), `HARLY_URL` must:

- Be an absolute URL with an `https://` scheme. Plain `http://` is rejected.
- Resolve to a routable public hostname. Harly rejects `localhost`, any
  `*.localhost` subdomain, the IPv4 loopback range `127.0.0.0/8`, the IPv6
  loopback `::1` (and `[::1]`), and the unspecified bind addresses `0.0.0.0`,
  `::`, and `[::]`.
- Contain no userinfo, query string, or fragment. Only scheme, host, and
  optional port are accepted.

Outside production, `http://` is allowed so local development against
`http://localhost:3000` continues to work.

If `HARLY_URL` is unset, Harly falls back to the legacy `NEXT_PUBLIC_APP_URL`
or `BETTER_AUTH_URL` and applies the same rules. Set `HARLY_URL` explicitly;
the fallbacks exist only for older deployments.

If validation fails, Harly throws at startup with a message such as
`HARLY_URL must use HTTPS in production.` or `HARLY_URL must use a reachable
public hostname, not a local or bind address.`. Fix the value in `.env` (or
your platform's secret manager) and restart the app.

<Warning>
  Behind a reverse proxy, set `HARLY_URL` to the public hostname candidates
  and integrations see — never the container's internal bind address. Values
  like `http://0.0.0.0:3000` or `http://127.0.0.1:3000` are rejected in
  production, and even when accepted they would produce broken links in
  emails, webhooks, and OAuth callbacks. See
  [proxy modes](/self-hosting/proxy-modes) for reverse-proxy setup.
</Warning>

## Required runtime values

```dotenv
HARLY_URL=https://hiring.example.com
DATABASE_URL=postgresql://user:password@postgres:5432/harly
BETTER_AUTH_SECRET=<independent-32-byte-secret>
AI_ENCRYPTION_KEY=<independent-32-byte-secret>
STORAGE_UPLOAD_SECRET=<independent-32-byte-secret>
CRON_SECRET=<independent-32-byte-secret>
METRICS_TOKEN=<independent-32-byte-secret>
HARLY_SETUP_SECRET=<independent-32-byte-secret>
HARLY_INITIAL_ADMIN_EMAIL=owner@example.com
```

`harly` generates independent values and writes `.env` with mode
`0600`. On managed platforms, store all values as secret variables rather than
plain configuration.

Secrets for `BETTER_AUTH_SECRET`, `AI_ENCRYPTION_KEY`, `STORAGE_UPLOAD_SECRET`,
`CRON_SECRET`, and `HARLY_SETUP_SECRET` must contain at least 32 bytes (or
32+ bytes when base64-decoded).

## Storage

### Local volume

```dotenv
STORAGE_PROVIDER=local
UPLOADS_DIR=uploads   # default — relative to the installation directory
```

Back up the `uploads` volume together with PostgreSQL. Do not use local storage
on platforms with ephemeral filesystems (Render, Railway, Fly.io).

### S3-compatible storage

```dotenv
STORAGE_PROVIDER=s3
S3_BUCKET=harly-production
S3_REGION=us-east-1
S3_ACCESS_KEY_ID=<access-key>
S3_SECRET_ACCESS_KEY=<secret-key>
S3_ENDPOINT=https://s3.example.com    # optional — for R2, MinIO, or other providers
S3_PUBLIC_URL=https://cdn.example.com  # images only; never expose resumes publicly
```

`S3_ENDPOINT` and `S3_PUBLIC_URL` are optional for AWS but required for
Cloudflare R2, MinIO, and other S3-compatible providers. All four core S3
variables (`S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`)
are required when `STORAGE_PROVIDER=s3`.

Candidate files must live in a private bucket. Disable public access, object ACLs,
anonymous `GetObject`, and public CDN origins. Harly serves resumes through an
authenticated application route with `Cache-Control: private, no-store`; do not
configure a public CDN path for `workspaces/*/resumes/*`.

## Scheduler and metrics

The scheduler authenticates private cron routes using `CRON_SECRET`. Harly
exposes a Prometheus-compatible metrics endpoint:

```http
GET /api/metrics
Authorization: Bearer <METRICS_TOKEN>
```

Never put either secret in a URL or query string. GET and query-string
secrets are rejected. The metrics endpoint returns `401` without the token;
with `Accept: application/json` it also returns queue and cron summaries.

Workspace members can read coarse connector health at
`GET /api/health/integrations` with their Harly session. Members who can manage
integrations also receive per-provider status and the last sanitized error; the
endpoint never returns credentials or webhook secrets. To alert on failed cron
runs, high SSE p95 latency, and elevated HTTP 5xx rates, import
`docs/observability/prometheus-alerts.yml` from the repository into your
monitoring stack. The full job list and intervals are in the
[scheduler runbook](/self-hosting/operations#scheduler-and-queue-runbook).

The scheduler handles the email outbox, domain-event replay, webhooks dispatch,
interview calendar sync, mailbox sync, document expiry, retention enforcement,
e-sign reconciliation, scheduled reports, and governed evaluation jobs.

## Resource profiles

The CLI selects a resource profile based on the available free memory at
install time. You can override any value in `.env`.

| Profile | When selected | App RAM | PostgreSQL | Scheduler | Caddy |
| --- | --- | --- | --- | --- | --- |
| `compact` | Free RAM < 1.5 GB | 1024 MB | 384 MB | 192 MB | 128 MB |
| `standard` | Free RAM 1.5–3.5 GB | 1536 MB | 768 MB | 256 MB | 256 MB |
| `performance` | Free RAM > 3.5 GB | 3072 MB | 1536 MB | 512 MB | 256 MB |

Override individual limits in `.env`:

```dotenv
# Compact profile overrides (2 GB VPS):
HARLY_APP_MEMORY=1024m
HARLY_APP_NODE_OPTIONS=--max-old-space-size=640
HARLY_POSTGRES_MEMORY=384m
HARLY_MIGRATE_MEMORY=512m
HARLY_SCHEDULER_MEMORY=192m
HARLY_CADDY_MEMORY=128m
```

## Database connection pools

Each Harly process keeps its own PostgreSQL connection pools. The generated
`compose.yaml` forwards these variables to the app, scheduler, and migrate
services. Leave them unset to use the defaults.

| Variable | Default | Purpose |
| --- | --- | --- |
| `HARLY_DB_POOL_MAX` | `10` | Main application pool used by web requests and background jobs. |
| `HARLY_DB_LOCK_POOL_MAX` | `20` | Reserved pool for cron overlap guards. Each running cron job holds one connection for its whole run. |
| `HARLY_DB_MAILBOX_LOCK_POOL_MAX` | `4` | Reserved pool for per-mailbox sync locks. |

Lock pools are separate from the main pool so that long-running jobs holding a
lock can never take every connection away from web requests. The cron and
mailbox lock pools are also separate from each other because the mailbox-sync
cron holds a cron lock while it takes a mailbox lock. Harly opens a lock pool
only when a process first takes that kind of lock.

```dotenv
# Example: larger app pool on a busy installation
HARLY_DB_POOL_MAX=20
HARLY_DB_LOCK_POOL_MAX=20
HARLY_DB_MAILBOX_LOCK_POOL_MAX=4
```

Size the pools against PostgreSQL `max_connections` (`100` by default). A
single Harly process can open up to `HARLY_DB_POOL_MAX + HARLY_DB_LOCK_POOL_MAX +
HARLY_DB_MAILBOX_LOCK_POOL_MAX` connections, which is 34 with the defaults.
Multiply that by the number of Harly processes that connect to the database,
and keep the total below `max_connections` with headroom for backups,
`psql` sessions, and other clients. If you raise the pools, raise
`max_connections` on PostgreSQL as well, or lower the lock pools on small
installations.

## Optional integration credentials

Installation-level OAuth credentials enable each integration's connect flow.
All are optional. Workspace credentials are encrypted in PostgreSQL after an
administrator connects an account.

| Variable | Integration |
| --- | --- |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | Google Calendar and Google Meet |
| `MICROSOFT_CLIENT_ID` / `MICROSOFT_CLIENT_SECRET` | Microsoft Outlook and Teams |
| `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` | GitHub OAuth for the candidate portal |
| `LINKEDIN_CLIENT_ID` / `LINKEDIN_CLIENT_SECRET` | LinkedIn OAuth (candidate portal) |
| `ZOOM_CLIENT_ID` / `ZOOM_CLIENT_SECRET` | Zoom video interviews |
| `SLACK_CLIENT_ID` / `SLACK_CLIENT_SECRET` | Slack notifications |

Slack delivery history is retained for 90 days by default. Operators may set
`SLACK_DELIVERY_RETENTION_DAYS` between 30 and 730 days; the protected
webhooks-dispatch cron purges completed and dead-lettered records outside that
window.

ID and secret must always be set together — configuring only one causes a
startup validation error.

See [integrations overview](/integrations/overview) for provider-specific
redirect URIs and setup steps.

## Pinning third-party images

The Compose stack pulls `postgres:16-bookworm` and `caddy:2.10-alpine` by
floating tag. The optional e-signature profile pulls `docuseal/docuseal` at the
version in `HARLY_DOCUSEAL_VERSION` (default `3.3.4`; change it to upgrade
DocuSeal deliberately). The Harly image itself is always pinned by
`HARLY_IMAGE`. For fully reproducible deployments, pin the others by digest:

```bash
docker buildx imagetools inspect postgres:16-bookworm | head -3   # note the Digest
docker buildx imagetools inspect caddy:2.10-alpine | head -3
```

Replace the `image:` lines in `compose.yaml` with
`postgres:16-bookworm@sha256:<digest>` and `caddy:2.10-alpine@sha256:<digest>`.
A pinned image receives no security rebuilds, so review and bump the digests on
your own schedule.

## Updates and AI agents

All optional, with safe defaults.

| Variable | Default | Purpose |
| --- | --- | --- |
| `HARLY_RELEASE_MANIFEST_URL` | the public `release-manifest.json` on GitHub | Where **Settings → Updates** and the host updater read the stable release channel. Point it at a mirror. |
| `HARLY_DISABLE_UPDATE_CHECK` | `false` | Set to `true` on an air-gapped host. The app then never contacts the release channel. `harly update` on the host keeps working. |
| `HARLY_UPDATER_INTERVAL` | `60` | Host updater only (read from its environment, not the app's): seconds between polls, 15 to 3600. |
| `MCP_ALLOWED_ORIGINS` | empty | Extra browser origins, comma separated, that may call the [MCP server](/developers/mcp). Empty answers only your own origin and loopback. |
| `HARLY_MODELS_DEV` | on | Set to `0` so the AI model picker never contacts models.dev and uses only its built-in list. Use it on an air-gapped host. |
| `HARLY_ALLOW_LOCAL_LLM` | off | Set to `1` to let a [custom AI endpoint](/product/ai-features#custom-api-endpoint) use localhost or a private network address, for example Ollama, LM Studio, or vLLM on the same host or LAN. Restart Harly after changing it. |

Neither the bundled `compose.yaml` nor the one `harly init` writes forwards
`HARLY_MODELS_DEV` or `HARLY_ALLOW_LOCAL_LLM`. To use them, add them to the
shared environment block at the top of `compose.yaml` (`x-harly-env` in the
bundled file, `x-env` in the generated one).

The in-app updater needs the host updater service from the CLI; see
[Update from the app](/self-hosting/operations#update-from-the-app). `/mcp` is a
streaming endpoint: a reverse proxy must not compress or buffer it (the bundled
Caddyfile already does not).

## Security-sensitive settings

```dotenv
HARLY_ALLOW_PRIVATE_WEBHOOKS=false  # default
TRUSTED_PROXY_IPS=                  # comma-separated list, empty by default
```

`HARLY_ALLOW_PRIVATE_WEBHOOKS` should be set to `true` only for a controlled
internal deployment where outbound webhooks must reach loopback or private
addresses. In all other deployments, leave at the default. Harly blocks
loopback, private, link-local, and cloud-metadata addresses on all outbound
HTTP actions.

`TRUSTED_PROXY_IPS` lists the peer addresses of reverse proxies whose
`X-Forwarded-For` header Harly should trust. When the immediate peer matches
one of these values, Harly uses the leftmost forwarded address as the client
IP. Otherwise it falls back to the rightmost hop so the header cannot be
spoofed. This value drives what audit logs record for `ipAddress`, which
address workspace IP allowlists evaluate, and how per-IP rate limits partition
traffic.

Leave `TRUSTED_PROXY_IPS` empty when Harly is exposed directly or served
through the bundled Caddy proxy. Set it to the address (or comma-separated
addresses) that Harly sees as the TCP peer when running behind an external
reverse proxy, load balancer, or CDN. See
[proxy modes](/self-hosting/proxy-modes#trust-your-reverse-proxy-for-client-ips)
for concrete examples.
