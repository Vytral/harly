# @harly/telemetry

Collector for the anonymous, opt-in install telemetry sent by `@harly/cli` >= 0.7.0. A small Node handler with no framework. It runs as a standalone server (SQLite, VPS/Docker) or as a Vercel serverless function (Postgres, e.g. Neon).

The package is self-contained (no imports outside this folder, no dependency on `apps/web` or `packages/*`), so it can be moved to its own public repository unchanged.

## What is and is not stored

Stored per `(instanceId, event)`: `instanceId` (random UUID v4 generated by the CLI), `event`, `cliVersion`, `os`, `arch`, optional `deployMode` and `referral`, and two ISO UTC timestamps (`first_seen_at`, `last_seen_at`).

Never stored or logged: IP addresses, User-Agent, any other request header, query strings, cookies. The request log contains only `method route status duration`. The rate limiter keeps IPs in memory only as `HMAC(random per-process salt, ip)`; the salt rotates hourly, idle entries expire and the table is capped, so nothing survives a restart or links an origin across hours.

## Contract

Source of truth: `tooling/harly/src/telemetry.ts` and the "Collector contract" section of `tooling/harly/README.md`.

`POST /v1/events` with `content-type: application/json`:

```json
{
  "schema": 1,
  "event": "install_completed",
  "instanceId": "3f1c9a52-8d0e-4b7a-9c1d-2a6e5b8f0d41",
  "cliVersion": "0.7.0",
  "os": "linux",
  "arch": "x64",
  "deployMode": "caddy",
  "referral": "github"
}
```

Validation is strict (unknown keys are rejected). `os`, `arch` and `deployMode` must match `^[a-z0-9_-]{1,32}$`; `referral` is one of `github, search, friend, social, blog_video, other`.

| Status | When |
| --- | --- |
| 202 `{"ok":true}` | Stored (or refreshed). |
| 400 | Invalid JSON or payload. |
| 405 | Any method other than POST (`Allow: POST`; `OPTIONS` too, there is no CORS). |
| 413 | Body larger than the limit (2 KB by default); reading stops at the limit. |
| 415 | Content-type is not `application/json`. |
| 429 | Rate limited (`Retry-After` in seconds). |
| 503 | Storage failure (generic message, details are not exposed or logged). |

Resending the same `(instanceId, event)` is idempotent: no new row, `last_seen_at`, `cliVersion`, `os` and `arch` are refreshed, and `deployMode`/`referral` are updated only when present.

Other routes: `GET /healthz` (200 `ok`, never touches the database), `GET /readyz` (200 if the database answers, else 503) and `GET /v1/stats` (below).

## Configuration

All via environment variables (see `.env.example`).

| Variable | Default | Meaning |
| --- | --- | --- |
| `TELEMETRY_PORT` | `8787` | Listening port. |
| `TELEMETRY_HOST` | `127.0.0.1` | Listening address (`0.0.0.0` in containers). |
| `TELEMETRY_DATABASE_URL` | unset | Postgres connection string. If set (or `DATABASE_URL` / `POSTGRES_URL`, checked in that order) Postgres is used instead of SQLite. |
| `TELEMETRY_DB_PATH` | `./data/telemetry.db` | SQLite file (used only when no Postgres URL is set); its directory is created. |
| `TELEMETRY_STATS_TOKEN` | unset | Enables `/v1/stats`. Unset means the endpoint answers 404. |
| `TELEMETRY_TRUST_PROXY` | `0` (`1` on Vercel) | `1` uses the first `X-Forwarded-For` value as the rate-limit origin. Only enable behind a proxy that overwrites that header. |
| `TELEMETRY_RATE_LIMIT_PER_MIN` | `30` | Sustained requests per origin per minute. |
| `TELEMETRY_RATE_LIMIT_BURST` | `10` | Bucket size (burst). |
| `TELEMETRY_RATE_LIMIT_MAX_KEYS` | `10000` | Cap on tracked origins (oldest evicted). |
| `TELEMETRY_MAX_BODY_BYTES` | `2048` | Maximum request body. |

## Storage: SQLite instead of Postgres

SQLite (`node:sqlite`, built into Node >= 22.13, WAL mode, `user_version` migrations applied idempotently at startup) was chosen because the workload is one tiny upsert per install: no extra service to run, back up or secure, no native dependency, and a single file to snapshot. The trade-offs: one writer process on one host (no horizontal scaling or multi-region), the volume must be persistent and backed up (`sqlite3 telemetry.db ".backup out.db"` is safe while running), and ad-hoc analytics beyond `/v1/stats` means opening the file. For the expected volume (installs, not page views) this is far below any SQLite limit; if it ever outgrows it, the `Store` class in `src/db.ts` is the only thing to replace. `node:sqlite` is still marked experimental in Node, which is why the Docker image pins Node 24.

### Storage backends

Both implement the `EventStore` interface in `src/store.ts` with the same logical schema (`UNIQUE(instance_id, event)`, `INSERT ... ON CONFLICT DO UPDATE`, UTC timestamps, parameterized queries). `src/pgstore.ts` uses `timestamptz` and a `telemetry_schema` version table; the migration runs once per instance (memoized promise) under an advisory lock, so concurrent cold starts are safe.

Driver: `pg` with a pool of one connection. Each serverless instance serves one request at a time, Neon's pooled endpoint (PgBouncer) multiplexes instances, and `pg` also works against any ordinary Postgres, which keeps local development and tests on a plain container. `@neondatabase/serverless` would add HTTP/WebSocket transport that a stock Postgres cannot speak, with no benefit at this request volume.

## Develop and test

From the repo root (`pnpm install` first):

```bash
pnpm --filter @harly/telemetry dev        # tsx watch on :8787
pnpm --filter @harly/telemetry test       # vitest, in-memory SQLite, ephemeral ports
pnpm --filter @harly/telemetry typecheck
pnpm --filter @harly/telemetry lint
# Postgres tests run only when a disposable database is provided:
TELEMETRY_TEST_PG_URL=postgres://user:pass@localhost:5432/telemetry_test pnpm --filter @harly/telemetry test
pnpm --filter @harly/telemetry build && pnpm --filter @harly/telemetry start
```

### Try it with the real CLI

```bash
export TELEMETRY_STATS_TOKEN=local-dev-token   # example value only
pnpm --filter @harly/telemetry dev &

# Use a throwaway config dir so your real CLI preferences are untouched.
export HARLY_CONFIG_DIR="$(mktemp -d)"
export HARLY_TELEMETRY_URL=http://localhost:8787/v1/events
harly init --telemetry            # sends one event when setup finishes
harly telemetry status            # shows the endpoint and consent state
```

Then inspect the aggregates:

```bash
curl -s -H "Authorization: Bearer $TELEMETRY_STATS_TOKEN" http://localhost:8787/v1/stats
```

## Statistics

`GET /v1/stats` with `Authorization: Bearer <TELEMETRY_STATS_TOKEN>` (compared in constant time; 401 otherwise; 404 when no token is configured). It returns aggregates only, never instance ids:

```json
{
  "totalInstances": 42,
  "active30d": 17,
  "byReferral": { "github": 20, "unknown": 15, "friend": 7 },
  "byCliVersion": { "0.7.0": 40, "0.7.1": 2 },
  "byOsArch": { "linux/x64": 30, "darwin/arm64": 12 },
  "byDeployMode": { "caddy": 25, "external": 10, "unknown": 7 }
}
```

`active30d` counts instances whose `last_seen_at` is within the last 30 days. `unknown` means the optional field was not sent.

## Deploy on Vercel + Neon

1. In Vercel, create a project from the Harly repository and set **Root Directory** to `apps/telemetry`. Framework preset: Other. Set the Node.js version to 24.x (22.x also works). `vercel.json` already defines the build (`pnpm build`, output `public/`), the function (`api/index.ts`, `maxDuration` 10 s, 256 MB), the rewrites for `/v1/events`, `/v1/stats`, `/healthz`, `/readyz`, security headers and no CORS headers.
2. Region: edit `regions` in `vercel.json` (default `iad1`) to match your Neon region. Vercel does not allow env vars there, so change it in the file.
3. Storage tab, Marketplace: add **Neon** and connect it to the project. It injects `DATABASE_URL` / `POSTGRES_URL`; the collector picks them up and creates its table on the first request. No manual migration.
4. Environment variables: `TELEMETRY_STATS_TOKEN` (`openssl rand -hex 32`) to enable `/v1/stats`. `TELEMETRY_TRUST_PROXY` already defaults to `1` on Vercel, which overwrites `X-Forwarded-For`; set it explicitly only to override.
5. Domain: add `telemetry.harly.dev` in the project's Domains, then in Cloudflare create a `CNAME telemetry` pointing to the target Vercel shows (e.g. `cname.vercel-dns.com`), proxy status **DNS only** (grey cloud) so Vercel issues the certificate and sees the real client IP header.
6. Check: `curl https://telemetry.harly.dev/readyz` returns `ok`.

Serverless caveats:

- The in-memory rate limiter is best-effort and per instance: concurrent instances do not share it, and it resets on cold start. The real protection is the 2 KB body cap, strict validation and the idempotent upsert (a flood of the same id is one row). Add Vercel Firewall rate limiting on `/v1/events` if you need a hard limit.
- The collector reads `X-Forwarded-For` / `X-Real-IP` only in memory, to derive the hashed rate-limit key. Its own logs hold only method, route, status and duration. Vercel's platform request logs and observability tools record client IPs independently of this code; keep log drains off and review the project's log retention if the "no IP stored" promise must hold at the platform level.
- Free-tier Neon computes suspend when idle, so the first request after a pause is slower; the CLI's 2 second timeout may drop that event. This is acceptable for telemetry.

## Deployment (VPS / Docker, SQLite)

1. Point DNS for `telemetry.harly.dev` (A/AAAA) at the host.
2. Generate a stats token (`openssl rand -hex 32`) and put it in `deploy/.env` as `TELEMETRY_STATS_TOKEN`.
3. `docker compose -f deploy/compose.example.yaml up -d --build` from this folder. It runs the collector (`node:24-alpine`, non-root, data in the `telemetry-data` volume mounted at `/data`) behind Caddy, which obtains the certificate automatically.
4. `deploy/Caddyfile.example` has no access log (explicitly discarded) and overwrites `X-Forwarded-For`, so the compose file sets `TELEMETRY_TRUST_PROXY=1`. Without a proxy in front, leave it at `0`.
5. Back up the `telemetry-data` volume.

The CLI ships with `https://telemetry.harly.dev/v1/events` as the default endpoint; users can override it with `HARLY_TELEMETRY_URL`.

Shutdown is graceful on `SIGTERM`/`SIGINT` (in-flight requests finish, then the database is closed). Server timeouts: 10 s headers, 15 s request, 5 s keep-alive.
