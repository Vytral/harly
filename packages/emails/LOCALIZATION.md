# Email localization

The `locale` supplied to an email template must describe the recipient's language. It must not be copied from the sender's browser or a workspace administrator's settings. `resolveEmailLocale` accepts the six supported locale tags, ignoring case, and falls back to English if the recipient preference is missing or unsupported. The caller is responsible for finding the correct preference and passing it both to the template and its subject function. No recipient preference is read by this package.

All built-in system templates accept an optional locale, including the signature invitation and reminder. Pass the recipient locale to both the template and its subject helper (`getResetPasswordSubject`, `getVerifyEmailSubject`, `getWelcomeEmailSubject`, `workspaceInvitationSubject`, `signatureInvitationSubject`, and the other exported subject helpers). Existing callers may omit it and continue to render in English. The layout sets the HTML language from the same locale; fallback links, shared greetings, and product footer use localized messages. `SignatureNotice` and `CustomTemplateEmail` contain workspace-authored content; their headings, paragraphs, rows, button labels, and HTML remain as supplied by the caller.

The authentication sender currently uses the English constant for password reset. Wiring the recipient's stored preference through that sender, verification flows, and any queue or retry payload remains open. Do not infer a candidate's language from a recruiter's request. Decide how each recipient's preference is collected and stored before enabling localized sends, and retain the selected locale when an email is queued or retried.

The catalogs in `messages/` cover password reset, email verification, staff and portal sign-in links, portal password reset, welcome, workspace invitation, candidate rejection, stage update, application receipt, recruiter notification, offers, interview notifications, signature invitations and shared strings in English, Spanish, Brazilian Portuguese, German, French, and Dutch. Crowdin and catalog validation now include this directory. Amounts, dates and other caller-supplied values are retained as provided; callers must format dates and amounts for the recipient locale. Caller-supplied rejection messages, interview notes/reasons, signature notes, and custom workspace email content remain unchanged. Automated rendering tests cover all six languages, including localized subjects, HTML language, retained dynamic values, and plain-text output for signature invitations. Client-specific appearance and delivery are not covered; review rendered messages in supported mail clients.

Run `pnpm --filter @harly/emails typecheck` and `pnpm --filter @harly/emails test` after changes. Integration remains open: the authentication sender still uses the English password-reset subject; verification flows and queued/retried messages do not yet carry recipient preferences; other send callers must load the locale belonging to each recipient. Tests do not verify delivery, preference persistence, attachment behavior, or rendering in real mail clients. Do not infer a candidate's language from a recruiter's request.
