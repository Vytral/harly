# ADR-005: Governed candidate evaluation engine

## Status

Accepted

## Context

Harly supports workspaces without an AI provider and must still offer useful,
explainable candidate triage. Hiring data is sensitive and evaluation output
must be reproducible, auditable and safe to retain. A raw score generated by a
single function is not sufficient for enterprise deployments.

## Decision

Harly uses a neutral candidate-evaluation contract consumed by both provider AI
and the deterministic Harly Algorithm. Deterministic evaluations use a
versioned rubric and persist criterion-level evidence, status, source,
confidence, coverage, input/output hashes and a human-review flag.

The current `ai_evaluations` table remains a compatibility surface during the
migration, but new metadata and criterion results make the persisted contract
engine-neutral. A later migration may rename it to `candidate_evaluations`.

Evaluation work is represented by a durable `evaluation_jobs` row. Inline
processing is an optimization; the cron worker can reclaim pending or failed
work after a request or process crashes.

No automated evaluation may directly reject an applicant. Automation may
prioritize, tag, notify or create a review task. Rejection remains a human
action and the runtime guard also applies to legacy/imported workflow JSON.

## Rubric rules

- Job criteria are explicit keywords or recruiter-approved rubric criteria;
  arbitrary skills found in free-form job prose are not silently treated as
  requirements.
- `met`, `not_met` and `unknown` are distinct states.
- Unknown evidence is excluded from the score denominator but lowers coverage
  and can force human review.
- The score is a prioritization signal, not an employment decision.
- Rubric, engine and input versions are immutable evaluation provenance.

## Consequences

### Positive

- Recruiters can inspect the evidence behind each criterion.
- Scores can be reproduced after algorithm changes.
- AI and rules evaluations share one contract and UI.
- Crashes do not silently lose automatic evaluations.
- Sensitive derived artifacts can be deleted as one retention unit.

### Negative

- The schema and worker are more complex than a single upsert.
- Existing consumers must migrate from AI-specific naming over time.
- Workspace rubric editing and fairness reporting require additional UI and
  operational tooling.

## Operational requirements

- Run the generated database migration before deploying the worker.
- Monitor pending, failed and stale-running evaluation jobs.
- Revalidate rubric versions when job requirements change.
- Review local and regional employment-law requirements before enabling any
  automated selection policy.
